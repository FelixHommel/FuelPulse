# ADR 007: Domain-Specific Repository Interfaces Instead of Generic Storage

## Status

*Accepted*

## Context

The original design introduced a generic ```IRepository``` interface (```put```/```get```/```range```/```all``` keyed
by ```Collection``` + ```Key``` storing JSON objects), meant to be implementation-agnostic and reusable across future
modules. A ```FuelRepositoryAdapter``` translated this generic interface into the domain-specific ```IFuelRepository```
that the rest of the fuel module actually depends on.

In practice, SQLite [ADR 3](./003.md) is the only storage backend this project will ever ship. The generic JSON-blob
layer erases the exact querying capabilities (typed columns, indices, ranged ```WHERE``` clauses) that motivated
choosing SQLite in the first place, the adapter exists only to undo that erasure. Genericity was never needed for
prdouction flexibility. It actually was only ever needed so test could swap in something lighter than a real Database.

## Decision

Drop the generic ```IRepository``` abstraction and the adapter layer. Each module defines its own repository interface
expressed in domain terms, e.g.:

```cpp
class IFuelRepository
{
public:
    virtual ~IFuelRepository() = default;

    virtual void store(const Measurement&) = 0;
    virtual void storeStation(const Station&) = 0;
    virtual std::vector<Stations> loadStations() = 0;
    virtual std::vector<Measurement> loadMeasurements(const std::string& stationId, TimePoint from, TimePoint to) = 0;
};
```

The only production implementation is a concrete SQLite-backend class implementing the interface directly, with real
tabels, typed columns, and indices designed around the queries the module actually performs.

Genericity across *storage backends* is not a goal. Genericity across production/test is achieved by depending on the
interface, not by maintaining a second production-grade backend. A lightweight in-memory test double implementing the
same interface exists purely to isolate unit tests from SQLite. It is a test fixture not a maintained alternative.

## Consequences

### Pros

- Real SQL: typed columns, indices, and ranged queries live in SQLite where they belong
- One fewer interface and one fewer type to maintain
- The repository interface reads as domain intent instead of generic operations
- Separation of concerns
- Test doubles are trivial

### Cons

- No shared repository implementation across future modules, each module designs it own schema and queries independently
- Loses the "one abstraction fits all future modules" appeal. A future module must define its own repository interface
